# 开发与发布

## 分支约定

- `dev`：协作者开发与待审核修改。提交代码、测试和未发布说明，不修改版本号，不创建版本标签。
- `main`：稳定发布与实际运行。用户直接交给代理的修改在验证后自动合并发布，更新版本号、正式更新说明及版本标签；协作者的dev改动仍需用户审阅。
- 各部署实例的凭据、人格、训练资料、记忆、群号和日志不纳入仓库。

## 开发提交

在独立开发目录使用 `dev`，避免将运行目录切换到开发代码：

```sh
git switch dev
git pull --ff-only origin dev
npm test
npm run check:repo
```

检查修改内容后提交：

```sh
git status --short
git diff
git add <本次修改的文件>
npm run check:repo -- --staged
git commit -m "fix: 描述本次修改"
git push origin dev
```

也可在确认工作区文件均应提交后使用 `发布更新.cmd`。该脚本只允许在 `dev` 运行，只向 `origin/dev` 推送，不自动更新版本或推送其他远程。

## 合并稳定发布

1. 审核 `main..dev` 的改动和测试结果，先解决上线问题。
2. 确认 `main` 工作区干净，拉取远程，合并审核后的 `dev`。
3. 更新 `package.json` 的语义版本，将未发布记录整理为正式 `CHANGELOG.md` 条目。
4. 完成离线回归、仓库扫描和暂存区审查，提交发布记录，创建 `v<版本>` 标签。
5. 推送 `main` 和对应标签，检查 GitHub Actions；失败时修复具体错误。
6. 使用既有部署入口重新加载机器人，核对运行版本和 QQ 实际连接。代码修改通常无需重启 NapCat。

`dev` 不承载个人部署配置。发布后可将 `main` 的版本与日志提交同步回 `dev`，保持下一轮开发基线一致。
